# Wordweave 全库 UI 设计分析

日期：2026-11-05。依据：frontend-design、impeccable、refactoring-ui，以及已确认的产品需求与领域词汇。

## 结论

现有 UI 有可保留的身份：绿色、英文拼写的衬线字体、克制的导航和关系组对照结构，适合个人生词本。应以 Operate（收录、整理）与 Read（阅读、对照）模式评价，不适合增加营销式 hero、装饰动效或无关仪表盘。

主要不足是可读性与交互细节：次级文字过浅；控件边界及焦点过浅；遮挡揭示后的答案没有进入当前辅助技术名称；列表遗漏两行摘要限制；表单分组、草稿保护与移动端成员布局不够完善。建议保持现有视觉身份，按影响逐项改进。

记录 12 项改进：P0 0 项、P1 4 项、P2 7 项、P3 1 项。另有 1 项未经性能测量的风险，不计为已发生故障。P1 表示显著影响核心任务或有明确可访问性问题；P2 表示可绕过的体验与维护问题；P3 为视觉精简。

## 详细发现

### 1. [P1] 次级正文、字段提示与占位文字对比度不足

位置：[style.css:370](../../web/src/style.css#L370)、[style.css:474](../../web/src/style.css#L474)、[style.css:464](../../web/src/style.css#L464)。

依据最终 CSS 前景/背景计算，近似比值如下：

| 内容 | 前景 / 背景 | 比值 |
| --- | --- | ---: |
| 列表释义 | `#768370 / #ffffff` | 4.00:1 |
| 页面副标题 | `#839083 / #f7f8f4` | 3.13:1 |
| 表单提示 | `#98a18f / #ffffff` | 2.68:1 |
| 输入占位文字 | `#b1b9a8 / #fdfefb` | 2.00:1 |
| 小计数 | `#8e9c84 / #eef2e9` | 2.56:1 |

这些是正常显示的内容，不是禁用控件。小字号和低对比同时存在，对视力较弱用户尤其不利。普通文字最低 4.5:1，大字才有 3:1 例外，见 [W3C 对比度说明](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html)。

建议：先建立 `text-primary`、`text-secondary`、`text-muted` 三个语义角色并验证背景组合。通过空间和字重减轻次级信息，避免继续降低文字明度。绿色风格可保留。适用：`$impeccable colorize`、`$impeccable typeset`。

### 2. [P1] 功能性边框和焦点色太浅

位置：[style.css:37](../../web/src/style.css#L37)、[style.css:450](../../web/src/style.css#L450)、[style.css:817](../../web/src/style.css#L817)。

输入边框 `#dce3d5` 对输入底色 `#fdfefb` 约 1.30:1；焦点 `#78ac97` 对白色约 2.58:1。输入背景与白色表单也接近，边框是主要的控件边界。问题不应扩展到所有装饰分隔线。

建议：区分 `control-border` 与 `divider`，单独加深焦点色。保持既有可见轮廓并验证键盘状态。非文本功能对比参考 [W3C 1.4.11](https://www.w3.org/WAI/WCAG22/Understanding/non-text-contrast.html)。适用：`$impeccable harden`。

### 3. [P1] 遮挡答案揭示后，辅助技术仍只获得操作名称

位置：[StudyText.vue:25](../../web/src/components/StudyText.vue#L25)。

按钮始终用 `aria-label` 命名为“显示/收回释义（拼写）”，覆盖内部答案的名称。实时用键盘 Enter 揭示 effect 释义后，DOM 内答案已可见，但可访问性树只显示“收回释义，已选中”，没有答案文本。

影响：视觉用户能看到答案，辅助技术用户当前获得的仍只有操作。此结论来自源码与浏览器 AX，尚未使用真实屏幕阅读器验证所有浏览模式。

建议：将主动揭示后的答案作为独立可访问文本或关联说明提供；隐藏时仍不得泄漏答案。保留原生按钮和按压状态，不能简单删除标签导致隐藏答案提前暴露。适用：`$impeccable harden`。

### 4. [P1] 词条列表没有执行两行摘要限制

位置：[EntryList.vue:91](../../web/src/pages/EntryList.vue#L91)、[style.css:370](../../web/src/style.css#L370)；需求：`docs/product-requirements.md` §6.3。

实时 1440px 视口下，测试长释义高约 665.6px，旁边普通释义约 20.8px。长卡片让日期网格出现大片空洞，并将后续词条推远。这是已确认需求遗漏，不只是审美选择。

建议：仅对列表非遮挡释义做两行摘要，详情提供全文。关系组内仍完整换行；遮挡区域继续使用固定尺寸与内部滚动。适用：`$impeccable layout`。

### 5. [P2] 移动关系卡片内的两列过窄

位置：[style.css:1097](../../web/src/style.css#L1097)。

390px 视口下实测列宽约为 121.4px / 164.2px，长英文短语被拆成多行，长释义对应成员行高约 1436.7px。卡片没有横向溢出，但阅读效率差。

建议：窄屏成员采用拼写在上、释义在下；桌面保留左右对照。组内完整释义要求应保留，不通过截断解决。短内容可继续紧凑展示。适用：`$impeccable adapt`。

### 6. [P2] 成员操作与关系类型缺少分组间距

位置：[GroupForm.vue:148](../../web/src/components/GroupForm.vue#L148)、[style.css:424](../../web/src/style.css#L424)。

“收录缺少的词条”按钮后紧接关系类型字段；`.field + .field` 不匹配这里的结构。实时测量按钮底边与下一字段顶边差值约 0px，截图也可见标签贴在按钮下面。

建议：把成员搜索、候选列表与新增动作归为一个组，给整体组设置下间距。采用组外间距大于组内的规则，避免再堆孤立的 margin 特例。适用：`$impeccable layout`。

### 7. [P2] 桌面单列表单拉得过宽，候选长释义占据列表

位置：[style.css:712](../../web/src/style.css#L712)、[GroupForm.vue:140](../../web/src/components/GroupForm.vue#L140)。

`.group-form { max-width: none }` 覆盖通用表单 780px 限制。1440px 页面中，单列输入和说明横跨约千像素。候选选词区直接输出完整释义，测试长释义可以独占 280px 高的滚动区，其他候选藏在下方。

建议：为单列编辑内容保留合理最大宽度；候选区以拼写和短释义支持识别，详细内容可通过已有详情入口查看。这与最终关系卡片必须完整展示释义是两个不同场景。不需要把流程重做成多步向导。适用：`$impeccable layout`、`$impeccable distill`。

### 8. [P2] 保存按钮禁用原因不够就近

位置：[GroupForm.vue:175](../../web/src/components/GroupForm.vue#L175)、[GroupForm.vue:179](../../web/src/components/GroupForm.vue#L179)、[style.css:33](../../web/src/style.css#L33)。

保存同时受成员数、关系类型、上方未保存输入、新词收录面板和请求状态约束。已有草稿提示值得保留，但成员不足和未选类型没有紧邻保存区的具体解释。所有禁用按钮都显示等待光标，混淆“缺少条件”和“正在处理”。

建议：在保存附近显示首要缺项，如“再选择 1 个词条”“请选择关系类型”；只有实际请求时使用等待反馈。适用：`$impeccable clarify`。

### 9. [P2] 离开页面会静默丢弃未保存草稿

位置：[App.vue:75](../../web/src/App.vue#L75)、[GroupForm.vue:178](../../web/src/components/GroupForm.vue#L178)、[EntryDetail.vue:93](../../web/src/pages/EntryDetail.vue#L93)。

实时验证：在建组说明输入测试草稿，点击全部词条再后退，说明恢复为空，没有离开确认。词条编辑取消和路由重建也没有 dirty-state 保护。

建议：仅在实际修改后增加轻量离开确认，涵盖导航和全局搜索；保持“新词独立保存”的既有规则，不回滚已经收录的数据。暂不需要复杂自动保存。适用：`$impeccable harden`。

### 10. [P2] 动态编辑与路由缺少焦点交接

位置：[EntryDetail.vue:82](../../web/src/pages/EntryDetail.vue#L82)、[main.ts:22](../../web/src/main.ts#L22)。

实时点击编辑词条后，触发按钮被移除，`document.activeElement` 为 BODY，输入框未获焦点。路由目前只负责滚动；缺少全局标题焦点策略、跳过导航入口，页面标题也一直相同。

建议：打开编辑后聚焦首字段；取消后回到触发按钮；路由切换提供可预测的主内容焦点与页面标题。可利用已有 `main#main`，无需引入焦点管理框架。收录页已有局部自动聚焦，应保留。适用：`$impeccable harden`。

### 11. [P2] 缺少最小设计 token，统一修正成本高

位置：[style.css:1](../../web/src/style.css#L1)。

1242 行样式没有 CSS custom properties，字号覆盖 9、10、11、12、13、14、15、16、18、20、22、23、24、25、26、27、28、30、38、42、46px，字重也有 550、650 等中间值。圆角、边距、颜色依赖局部选择。

影响：无法一次可靠修正低对比文字、功能边框与层级，后续组件容易漂移。不能把每一个不在 skill 标尺中的像素都当用户故障；两种字体、不同语义的圆角也不必机械统一。

建议：抽取最常用的文字、背景、功能边框、焦点、间距和字号角色，建立一小套尺度即可。不要求引入组件库、完整色阶或暗色模式。适用：`$impeccable extract`（作为一般实现建议；正式修正可使用 `$impeccable document` 配合局部整理）。

### 12. [P3] 重复英文 eyebrow 稀释中文任务信息

位置：[EntryList.vue:44](../../web/src/pages/EntryList.vue#L44)、[EntryDetail.vue:145](../../web/src/pages/EntryDetail.vue#L145)、[style.css:277](../../web/src/style.css#L277)。

“YOUR WORD COLLECTION”“RELATION GROUPS”“IN YOUR COLLECTION”重复页面标题语义，10px 加字距提供了模板式装饰，几乎没有额外导航信息。

建议：移除这些重复标记，保留 Wordweave 标识与一处轻量品牌文案。英文拼写的衬线字体服务于内容，不应一起移除。详情标题区的“继续收词”也可降为文字操作。适用：`$impeccable distill`。

## 性能风险与未定事项

- `BrowseGrid.vue:29–33` 在循环内读取 `getBoundingClientRect()` 后立即写入网格位置，存在反复触发布局的风险。建议先批量读高度，再批量写位置。没有进行长列表性能剖析，不能声称已观察到卡顿，也不据此引入虚拟列表。
- 多数紧凑按钮未达到 44px 舒适触摸目标，可优先放大移动端常用操作。但 WCAG 2.2 AA 最低是 24px，且存在间距等例外，不能把所有小于 44px 的控件自动报为违规。见 [W3C 目标尺寸说明](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html)。
- 删除确认解释了哪些关系组保留/删除，这是优点；最终确认按钮仍沿用绿色，且顶部建组按钮仍在，可后续收敛确认时的动作层级。没有执行实际删除测试。

## 应保留的设计与实现

1. 两个主导航、常驻搜索和位置一致的新建入口，任务模型清楚。
2. 绿色与英文衬线拼写形成基本身份；本地系统字体、不依赖 CDN 符合产品约束。
3. 词条与说明命中的关系组分开，组边界清楚；当前成员用文字与背景双重提示。
4. 遮挡区域固定占位、详情入口分离、空说明省略、学习模式下说明折叠，符合学习任务。
5. 原生 button/select/checkbox、有标签输入、alert/status、统计 aria-live、按压状态和错误重试已建立可访问性基础。
6. 重复词条/组有已有记录入口；删除前明确说明后果；新词独立保存的提示能减少误解。
7. 前端依赖轻量，构建 JS 约 132.56KB（gzip 47.92KB），CSS 约 17.32KB（gzip 4.46KB）；没有不必要的装饰动画或图片负担。

## 典型用户影响

- 初次使用者：能找到收录入口，但到建组保存区后需要回看成员数和类型，禁用原因不够直接；不需要额外强制引导流程。
- 经常整理长说明的用户：最受列表高卡片、选词区长释义与草稿丢失影响，应优先保障内容编辑的连续性。
- 键盘及辅助技术用户：原生控件可操作，但进入编辑后焦点丢失；揭示答案后 AX 仍只有“收回释义”，完整学习闭环存在障碍。

## 建议执行顺序

1. 修复 P1：文字、控件/焦点对比，主动揭示答案语义，列表两行摘要。
2. 修复表单：成员分组间距、保存缺项提示、候选摘要及编辑宽度。
3. 修复移动阅读与编辑连续性：成员上下布局、草稿保护、焦点交接。
4. 抽取最小 token 并移除重复装饰；最后使用 `$impeccable polish` 统一细节。

这些建议不需要改变关系模型、引入组件库、增加背诵计划或重做视觉身份。修复后重跑 `$impeccable audit`，重点复核高影响项而非只追逐分数。
